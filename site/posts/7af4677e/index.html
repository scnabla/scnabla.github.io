Codex的Git提交与推送SKILL配置

发表于2026-09-05|更新于2026-09-19|AI

当前方案解决什么问题

直接执行 git add .、git commit 和 git push，容易把无关文件一起提交，也可能漏掉敏感信息、提交身份和远端分支检查。

现在的流程是：主代理先检查，再展示忽略项、待暂存文件和简短命令；用户明确选择操作范围后，主代理执行并自动验证。不再调用推送子代理，也不再打开终端让用户手动提交。

这里的三个 Git 动作分别是：

  • 暂存：把本次选中的改动放入待提交清单，还没有生成版本记录。
  • 本地提交：把暂存内容保存为本地版本记录，还没有上传。
  • 远端推送：把本地提交上传到指定远端分支。

本文描述的是个人配置中的工作约定，不是 Codex 默认会自动执行的所有行为。

本文负责哪些操作

本文只介绍 safe-git-github-workflow，使用 git 完成暂存、本地提交、普通推送和结果验证，不要求安装或登录 gh。

Release、PR、Issue、Actions 的配置、操作流程和完整 SKILL 已单独整理到《Codex的GitHub平台操作SKILL配置》。需要先推送代码再执行平台操作时，先完成本文流程，再进入对应的平台操作流程。

Git Skill 的七个步骤

1. 检查工具与运行环境

只从系统 PATH、用户级或系统级安装目录寻找 git，核验实际路径及版本。即使 PATH 包含项目目录，也不使用项目中的同名程序；项目自己的测试、构建脚本及依赖仍按项目配置使用。

仅本地提交不要求远端认证。需要连接远端时，先检查运行账号、Git 凭据助手和存储方式。

这套 Windows 配置特别处理沙箱账号与正常登录用户不一致的情况：使用 Git Credential Manager（GCM）的 wincredman 存储时，在第一次远端查询前申请宿主用户环境执行，不先在沙箱里试错。无法可靠确认环境时，也先申请宿主只读检查。

不会通过修改 safe.directory、代理或凭据存储绕过限制，也不会仅凭沙箱认证失败就要求用户重新登录。获准使用宿主环境，不等于已经获准推送。

2. 审查敏感隐私信息与忽略规则

核对仓库、远端、分支、可见性和本次改动范围。仓库可见性不明时，按公开仓库检查。

检查范围不仅是当前文件，还包括已有暂存内容、提交说明、作者和提交者信息、远端 URL，以及全部待推送提交。敏感内容即使在后来的提交中删除，也不能据此认定历史已经安全。

发现令牌、密码、Cookie、私钥、带凭据 URL 或无关隐私时停止，只报告问题类型与位置，不回显敏感值。

明确不应提交的本地文件、生成文件，在任务范围内补充到 .gitignore 并核验效果。.gitignore 自身也要审查；忽略规则不能自动移除已跟踪文件或历史内容。

3. 确认提交身份

创建提交前，核对最终生效的作者和提交者姓名、邮箱及配置来源，并等待用户确认。

本次已经明确确认相同身份时不重复询问；不擅自修改全局 Git 身份。只选择“暂存”时，不需要提交身份确认。

4. 检查并展示操作预览

先完成项目要求的必要测试或构建。检查失败、暂存区混有无法区分的无关改动，或文件范围不明时停止。

通过后，简短说明仓库位置、审查结果、拟用身份、目标远端分支及全部待推送提交范围，再按以下顺序展示。

当前忽略项

先展示当前实际被忽略的文件或目录，并区分：

  • 已有忽略：当前生效，本次没有变化。
  • 新增忽略：本次新增加的忽略项。
  • 修改忽略：说明规则修改前后的范围。
  • 删除忽略：单独列出取消忽略的项，不表示删除文件。

规则变化与实际匹配文件要区分；暂时没有匹配文件的规则也应说明。没有忽略项或本次没有变化时，明确写“无”。

5. 选择并等待确认

展示完忽略项、待暂存文件和命令后，给出四个选项：

  1. 暂存
  2. 暂存+本地仓库提交
  3. 暂存+本地仓库提交+远端推送
  4. 补充/调整说明

此时主代理暂停，等待明确回复，不预选代答，也不一边把问题放进队列、一边继续暂存、提交或推送。

前三项只授权本次展示的准确目标和范围。推送会把内容上传到远端，其他人可能获取；事后撤销不保证能够收回已经传播的内容。

选择第 4 项后，用户可以补充文件范围、提交说明或目标分支等要求。补充完成后从第 1 条重新核对，但不把全部操作机械地再做一遍：

  • 未变化且仍有效的工具检查、审查、测试和身份确认直接复用。
  • 本次同一操作的准确目标、内容、范围和影响均未变化时，不重复申请仍有效的授权。
  • 只重新检查受影响或失效的部分，对新增、变化范围重新确认。
  • 已完成的操作不重复执行，不沿用历史任务授权或绕过工具权限审批。

回到第 5 条时，只询问尚未明确的执行选择或变化范围。补充说明本身不等于同意执行。

6. 按选择执行

主代理先复核文件内容、暂存区和目标没有变化，再逐步执行：

  • 选项 1：准确暂存，核验完整暂存内容后进入结果验证，不创建提交。
  • 选项 2：准确暂存、核验，再按已确认说明创建本地提交。
  • 选项 3：完成选项 2，核验实际提交和全部待推送内容，再推送到已确认的远端分支。

实际暂存使用 git -C 指定仓库，使用 git add -- 加准确文件名单，不使用 git add .、git add -A 或 git commit -a。

各命令分别执行，任一步失败或结果不符就停止后续写操作，不自动重试、回滚或绕过 Hook。只要求推送已有提交时，单独确认推送，不暂存其他改动、不制造空提交。

7. 自动验证并反馈

操作后立即只读验证，不再等待用户回复“我已经手动执行完了”。

已执行操作 验证内容
仅暂存 暂存文件和内容是否符合确认范围，当前提交是否未变
本地提交 提交哈希、标题、身份、文件范围是否正确
远端推送 远端目标分支哈希是否与实际推送提交一致

所有情况都检查工作区、暂存区和剩余改动，简短报告实际完成情况及状态变化。

远端无法查询时明确写“推送结果未核实”。本地提交成功但推送失败时，分别报告，不能把两者混为成功。

不会随普通推送自动执行的操作

这个 Git Skill 不会顺带强推、改写历史、删除远端分支、创建或删除标签，也不会自动修复构建失败的代码。

Release、PR、Issue、Actions 等操作由独立的 GitHub 平台 SKILL处理，具体目标、身份和授权要求见该文。

对于通过 GitHub Actions 部署的网站，推送可能触发已配置的工作流，但“提交已经到达远端”和“网站部署成功”是两件事。需要检查部署时，应单独说明，不能仅凭推送成功就宣称上线完成。

常见问题

为什么不继续使用 git-delivery 子代理

当前选择只保留 Skill 方式。主代理直接读规则、审查、询问和执行，不再传递任务给专用推送子代理。因此，旧文中的子代理 TOML、独立模型配置和继续调用原子代理的步骤都不再适用。

Skill 的正文在使用时仍会进入主代理上下文，并不是完全不占上下文。这里的做法是保持规则简短，并将 GitHub 平台功能拆开，只在需要时读取。

文件已经暂存，为什么还要核对

已有暂存区可能包含本次任务以外的内容。主代理必须区分已暂存和待暂存的改动；不能确认归属时停止，不擅自清空暂存区，也不直接把全部暂存内容提交。

为什么预览了命令却还没有提交

预览用于让用户看清提交说明和远端目标，不代表执行授权。只有明确选择对应操作、满足身份确认和其他必要权限后，才执行。

推送失败是否需要重新提交

不需要因为推送失败重复创建同一个提交。本地已经成功的提交应保留并报告；处理失败原因后，在确认准确范围的前提下继续推送已有提交。

是否一定需要 gh

普通 Git 暂存、提交和推送不需要。gh 用于配套文章中的 GitHub 平台操作，它的登录状态与 Git 推送使用的凭据分别核验。
